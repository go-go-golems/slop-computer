SLOP3-009 · design brainstorm · 3 November 2026

slop-computer as a framework for hosting artifacts

How the code could be reorganized so that the pieces slop already has, such as the claude.ai contract runtime, a sample backend with budgets, documents over SQLite, sign-in and the verb table, become building blocks that other hosts can reuse. It also covers how this fits the existing verb-oriented design.

brainstorm, not a plan of record repo: go-go-golems/slop-computer after SLOP3-008 (PR #20) APIs may change

1Where the code is today

slop has one good unifying idea already: the verb table. A verb is one named operation with arguments, a scope (read or write), an authority floor (authz.Action) and a Run function. The CLI, the HTTP API at /api/v1 and eval programs are all generated from it. Trusted Go modules for actors, added in SLOP3-002, are verb calls too: a modFunc maps a JavaScript name such as people.setRole to a verb, and the call runs as the visitor through every check that verb applies.

Two doors do not use the table. The page protocol (the RPCs db.get, db.write, files.list, sample and the event stream) has its own dispatch in pkg/server/views.go. Actor modules (use('db'), use('sample')) are a third implementation, in pkg/actor. The result is that the same capability exists in two places, with two sets of checks.

2The idea in one paragraph

Make the verb table the one place where an operation exists, and treat everything else as a projection of it. A capability (in the contract's sense: db, sample, files, room) becomes a named bundle of verbs plus the client code and grant rule that expose them to a page. A door (the page protocol, the CLI, the HTTP API, MCP, actor use()) is a transport that turns its own request shape into verb calls with a principal. A domain (registry, identity, billing, LLM) owns its tables and registers its verbs. A host product such as today's multi-tenant slop is a choice of domains, capabilities and doors, wired together in one small main.

The point of the waist is that every rule which must hold for every caller lives at one level: who may call, whether the person must confirm, what the audit log records, and what the documentation says. Today those rules hold for the CLI and the API, and are re-implemented by hand in the page protocol.

3Verbs at the center

What a verb carries today

type Verb struct {
	Name      string        // group.name, e.g. "grant.set"
	Doc       string
	Args      []Arg         // name, type (string|int|bool|json), position, required
	Scope     Scope         // read | write: what a token's scopes must include
	AdminOnly bool
	Action    authz.Action  // the authority floor, checked before Run
	StoreArg  string        // which argument names the store the floor is about
	Run func(ctx context.Context, e *Env, p *access.Principal, a Args) (any, error)
}

That is enough for request/response operations made by a person or a token. The page protocol needs three more things, which is why it grew its own dispatch: a principal that is a viewer inside a view (with the view's path space, granted capabilities and policy cells), results that stream (sample deltas, subscriptions), and contract error codes rather than CLI ones.

Verb v2: enough for every door

type Verb struct {
	Name    string            // "db.write", "grant.set", "sample.run" (the name stays "verb")
	Doc     string
	In, Out *schema.Schema    // typed: doors derive CLI flags, MCP tool schemas, TS types, docs
	Effect  Effect            // Read | Write | Govern (asks the person) | Stream
	Subject Subject           // Platform | Store(arg) | View: what the authority check is about
	Floor   authz.Action
	Run     func(c Call, in json.RawMessage) (any, error)
}

// Call is what every Run receives, whichever door it came through.
type Call interface {
	context.Context
	Principal() *access.Principal // a person, a token, a store, or a viewer in a view
	View() *rt.View               // nil outside a page or an actor event
	Emit(v any) error             // stream a partial result (Effect Stream)
	Deps() Deps                   // what this verb's package registered with, not a global Env
}

Three changes do most of the work. Subject: View lets db.write be an ordinary verb whose authority check reads the view (its level, its rt.Space, its rules) instead of a store argument. Effect: Govern moves the confirmation flow from a flag on modFunc into the verb itself, so a governance change asks the person no matter which door called it: CLI, page, actor or MCP. Emit gives sample and subscribe a way to stream through the same table.

What it costs

db.query and db.get are hot: a page issues many. Going through the table adds a map lookup, a floor check and a principal per call. The store work dominates, so this should be measurable but small. Measure it before and after on TestLiveHostViews-sized traffic. The second cost is conceptual: verbs today are "commands an operator runs". Page RPCs as verbs means the table also holds hundreds of calls per second from browsers. Audit and docs then need a Hidden or Internal flag, so slop --help does not list db.subscribe.

4Capabilities as building blocks

A capability is the unit someone building a host actually wants to reuse: "give my artifacts sample", "give them db over my own storage". In the verb-centered model a capability is a Go package that contributes five things:

type Capability interface {
	Name() string                          // the contract's use() name: "sample"
	Verbs() []*verbs.Verb                  // what it adds to the table (sample.run, sample.cancel, …)
	Offer(v *rt.View, m *rt.Manifest) bool // is it granted in this view (manifest + policy)?
	Policy() []policy.Cell                 // the cells an admin sets (sample: audiences, model tiers)
	Runtime() fs.FS                        // its piece of claude.js (sample.ts), optional
	Migrations() fs.FS                     // its tables in system.db or in stores, optional
}

The page door asks each capability whether it is offered, sends the granted list in the view's hello, and routes sample.* RPCs to the table. The actor door builds use('sample') from the same verbs, the way verbModule builds trusted modules today. A conformance suite per capability, run against the contract's type definitions, checks that the shapes and error codes match claude.ai.

5Worked example: sample as a block

sample is the clearest case for reuse. Any host of claude.ai artifacts has to answer "what happens when the page calls claude.use('sample')?", and the answer needs the same five parts everywhere. There is a backend that runs a model, a meter that charges someone's budget, and a policy that says who may call it at which tier. A tool loop runs page-defined tools in the browser while the model waits. And a streaming channel carries onText deltas. slop has all five, split across pkg/server/sample.go (298 lines, page side), pkg/actor/sample.go (actor side) and pkg/llm (backends and the ledger).

// caps/sample: the interfaces a host fills
type Backend interface {
	Run(ctx context.Context, req Request, out func(Delta) error) (Result, error) // tiers, tools, images
	Limits(ctx context.Context, tier string) Limits
}
type Meter interface {
	Reserve(ctx context.Context, payer string, est Usage) (Hold, error) // refuse before running
	Settle(ctx context.Context, h Hold, used Usage) error
}

// slop wires it to what it has; a desktop host would pass a local model and sample.NoMeter
cap := sample.New(sample.Config{
	Backend: llm.Router(cfg.LLM),   // tiers → models
	Meter:   ledger.Meter(sys),     // the budget ledger
	Payer:   billing.PayerOf,       // viewer, store or app owner
})

Two decisions in today's code become explicit parameters. The first is who pays for a page's sample (the viewer, the store, or the app's owner), which is Payer. The second is whether page tools may run while a turn is open: actors may not hold a transaction across a model call, which is why the actor side returns promises. Both are properties of the door and the host, not of sample itself.

6Approaches to modularity

"Modular" can mean four different boundaries. They differ in where the seam sits and what crossing it costs.

A · Packages in one module

cost: discipline · gain: clarity

Split by domain inside github.com/go-go-golems/slop-computer. Cycles are avoided by explicit registration at wiring time rather than init() into a global table.

Do this now, as features touch the code.

B · Capability plugins

cost: one interface · gain: products

Each capability implements Capability and is registered into a host. Building a different product means choosing a different set. Still compiled in, still one binary.

Falls out of A if packages are shaped this way from the start.

C · Separate Go modules

cost: releases · gain: reuse across repos

Extract identity, the contract runtime (claude.js plus the page protocol's types) and possibly store into their own modules, so go-go-host or a go-go-os backend can depend on them.

Only when a second project actually imports one.

D · Capability servers

cost: latency, auth hop · gain: any language

A capability runs as its own process and the host's verb table proxies to it, much as MCP servers work. It suits sample backends, or a files provider over a git forge.

Use for backends behind an interface (Backend, Meter), not for capabilities themselves.

A and B are the same work if a package's public surface is shaped like Capability or Domain from the first move. C and D are not alternatives to A and B. They are later steps applied to particular packages, once a second user or a second language exists.

7The framework shape

If the blocks exist, a host product is a short main. This is today's slop, rewritten as an assembly. The names are proposals, not existing APIs.

func main() {
	cfg := config.Load()
	p := host.New(host.Config{Data: cfg.Data})               // sysdb, stores, the verb table, the log

	p.Domain(identity.New(identity.Config{OIDC: cfg.OIDC, Admins: cfg.Admins}, identity.Hooks{
		Claimed: registry.MoveGrants,                         // slop's decision, passed in
	}))
	p.Domain(registry.New(), policy.New(), billing.Stripe(cfg.Stripe), llm.Budgets())

	p.Capability(db.New(), files.New(), room.New(), assets.New(), user.New(), downloads.New(),
		sample.New(sample.Config{Backend: llm.Router(cfg.LLM), Meter: llm.Ledger()}),
		storage.New())                                        // the DO-shaped actor API

	p.Door(pages.New(cfg.Hosts),                              // main, live, static, sandbox hosts
		cli.Verbs(), api.New("/api/v1"), mcp.New("/mcp"), actors.New())

	log.Fatal(http.ListenAndServe(cfg.Listen, p.Handler()))
}

Allowed

  • doors → verbs, rt, access
  • caps → domains, core, verbs (to register)
  • domains → sysdb, core, verbs (to register)
  • host → everything (it is the wiring)

Forbidden

  • verbs → any domain or capability
  • caps, domains → doors, net/http, goja
  • identity → any slop package except sysdb
  • one domain → another domain's tables (go through its verbs or exported functions)

The rules can be checked mechanically: a test in host/ runs go list -deps on each package and fails on a forbidden edge. That keeps the map honest after the people who drew it have moved on.

10Getting there: split as you go

The earlier decision stands: no PR only moves code, and each feature PR moves the code it touches into place. The difference now is that SLOP3-008 has left two obvious first moves, and the verb-table change can be introduced as a shim, so old and new verbs coexist.

  1. pkg/registry from pkg/server/registry.go. The file needs only a principal and verb calls. The mount-template code and LastChange follow. The check is that TestRegistryDocuments passes unchanged.
  2. caps/db. The page RPCs and the actor's use('db') resolve through rt.Space in one package. This is the first visible gain, since actors get aliases and _stores. The check is the path-space tests plus an actor test reading through an alias.
  3. caps/sample with Backend and Meter. Merge server/sample.go and actor/sample.go. The check is the sample tests on both sides.
  4. Verb v2 as a shim. Add Call, Effect and Subject while old verbs keep working through an adapter. Register db.* and files.* as Subject: View verbs, and delete the RPC switch.
  5. Callbacks to log followers. Replace AccessChanged and the other two with a follower of system _changes in the page door.
  6. The MCP door, generated from the table. It costs little once inputs are typed, and it is the first product-level payoff.
  7. identity to the reuse rules (no slop imports, hooks, its own migrations) when a second project needs logins.
  8. host.New and a second product (the desktop host) as the proof. Do this last, when something wants it.

11Open questions

  • Schemas: from Go types or hand-written? Generating JSON Schema from input structs keeps one source of truth; hand-written schemas give better MCP and CLI docs. glazed's field definitions are a third option, already used for CLI flags elsewhere.
  • Do page RPCs belong in the same table as operator verbs? The alternative is two tables over one Call type. That keeps slop --help clean but splits docs and audit again.
  • Where does each capability's TypeScript live? Next to its Go package (caps/sample/sample.ts), with claude.js assembled from the granted set? Or does web/runtime stay one package for tooling reasons?
  • Is the contract runtime its own product? claude.js plus the page protocol is what every artifact host needs. Published as an npm package with a Go server half, it would be the most reusable block of all.
  • One system.db or one per domain? Shared transactions across registry and identity are used today (claims move grants). Per-domain migrations inside one file keep that.
  • What is the second product? The desktop host, an agent host, or another project's need for identity. Whichever comes first decides which of steps 6 to 8 is worth doing.
